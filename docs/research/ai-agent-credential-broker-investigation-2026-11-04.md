# kinko: AIエージェント向け認証・権限委譲の調査指示書

- 区分: **調査・設計依頼（実装指示ではない）**
- 作成日: 2026-11-04
- 対象: Windows上で動くCodex / Claude Code / OpenCode等と、SSH先のLinuxサーバー
- 公開範囲: **公開してよい一般化された手順・設計のみ**
- 最優先: AIの自律性を維持しつつ、秘密情報の露出面と管理権限の過剰委譲を縮小する
- 注意: 本文の構成・保存形式・接続方式は**設計検討用の仮想ユースケース**であり、特定個人・組織の実構成を確認・記述したものではない

> **この文書だけを根拠に、実環境の認証情報を読み取ったり、実サーバーへ接続したりしないこと。**
> まずリポジトリと公開情報、秘密を含まないローカルのメタデータのみを確認する。
> 不明点は「未確認」と記録する。権限が必要な作業は別途、人間の明示的な承認を求める。

## 0. 読み始める前の指示（ローカルAI向け）

あなたは *kinkoのセキュリティ設計担当* として、現状確認と比較検討だけを行う。
本依頼では**コード変更、動作環境の移行、資格情報の取得、サーバー操作はしない**。

作業開始時に以下をこの順序で読む。

1. リポジトリの `AGENTS.md`、`CLAUDE.md` と各AIツールの適用済みグローバルルール。
2. `README.md`、`main.go`、`internal/cli/`、`internal/vault/` の関連実装・テスト。
3. `doxguard.ci.json`、既存のgitleaks / doxguard / pre-commit / GitHub Actionsの設定。
4. 必要なら既存PR（特に**Draft PR #2**）を「未マージの候補」として別途比較する。mainに存在する実装と混同しない。

矛盾する指示がある場合は、上位の安全制約、リポジトリの既存規約、人間による承認を優先する。
ローカルの非公開ルールや成果物を公開リポジトリへ転載しない。

## 1. 背景・解決したい問題

**一般的な設計ケース**として、AIコーディングツールが開発マシンからSSH接続し、必要に応じてリモートの `sudo` を使い、調査・修正・テスト・サービス操作を継続する状況を想定する。認証情報がリポジトリ外の設定ファイルに置かれるケースも検討対象とするが、実際の環境での採用状況は確認していない。

この方式はGitへの誤コミットを防ぐ一方で、**同じOSユーザー・実行権限を持つAIがファイル内容を読める場合には、リポジトリ外というだけでは隔離にならない**。また、パスワードを隠しても、無制限の操作を許可すると誤操作・プロンプトインジェクションの影響は残る。

求めるのは「AIに秘密を知らせない」だけではない。

- 定型的な認証・調査・テスト・デプロイ準備は、**最初の委譲後に人間を待たず自律実行**できること。
- 事前に許可したSSH接続・特定サービス操作は、秘密鍵やsudoパスワードの実値をAIへ返さず実行できること。
- 想定外・高リスク操作だけが承認待ちになること。承認後には**期限・対象・操作を限定**して再開できること。
- 権限の利用・拒否・失効を監査でき、ポリシーはAI自身が書き換えられないこと。
- 既存の `kinko add/get/run/export`、age保管庫、doxguard/gitleaksを不必要に壊さないこと。

**作業範囲は調査と提案まで**。本ドキュメントのPRは新しいBrokerの実装・導入を承認するものではない。

## 2. 絶対に守る制約

### 2.1 禁止事項

- `.env`、`.toml`、秘密鍵（OpenSSH/PEM等）、パスフレーズ、sudoパスワード、APIキー、PAT、Cookie、トークン、認証済みセッション、Windows資格情報、秘密を含むログ/履歴の**実値を開く・コピー・grepする・モデルへ投入する・出力する**こと。
- 環境変数の値を列挙するコマンド（例: `env`、`printenv`、`Get-ChildItem Env:`）、認証情報のあるファイル全体のダンプ、ファイル内容の試し読み。
- 実サーバーへのSSH接続、sudo実行、認証の試行、ポートスキャン、接続テスト、資格情報の検証。読み取り専用コマンドであっても**実サーバーには接続しない**。
- Windowsの設定変更、資格情報の移動、SSH Agentの起動・登録・解除、sudoersの変更、プロキシ/DNS/ファイアウォール変更、パッケージのインストール、バックグラウンドサービス起動。
- リポジトリへのコミット・push・PR作成・マージ、外部サービスへの設定アップロード、公開CIへの内部情報の提供。**この調査タスクを受けたローカルAIは変更しない。**
- 調査のために実際の権限境界を迂回する実験。悪用手順を実システムで試さない。

「内容は見ないがファイル名は一覧化する」場合も、パスや名称自体が機密情報になり得る。**必要性が説明できない一括列挙はしない。**
利用者が明示的に承認しない限り、秘密に近接するディレクトリを再帰走査しないこと。

### 2.2 許可される範囲

- 公開リポジトリのREADME、LICENSE、設計資料、ソース、テスト、公開Issues/PRを読む。
- kinko自身の公開コード・設定・テストを読む。
- ローカルOSの**秘密を含まない**バージョン、SSHクライアント/Agentの利用可否、AI起動方式、サンドボックス方式、OSアカウント間の分離方式などのメタデータを、必要最小限で確認する。
- 管理者権限を要しない静的確認のみ実施する。表示にユーザー名、端末名、ホスト名、パス、鍵識別子、サービス固有名称が混ざる場合は**表示・保存前に一般化**する。
- 判断不能な箇所は、再現に必要な秘密を求めず「未確認」「利用者による手動確認が必要」と書く。

ローカルAIへの「読み取らないで」というプロンプトは、OSレベルのアクセス制御ではない。
**実値をモデルに見せない保証が要る作業は、別OSユーザー、VM、独立Broker等の境界で行う。**

### 2.3 レポートの取り扱い

- 公開可能な設計書は、架空のホスト名 `example-host`、架空のユーザー `aiworker` 等だけを使う。
- 実環境の確認メモは原則リポジトリ外の非公開領域へ置く。既存運用で `docs/local/` が許可される場合だけそのgitignored領域を用いる。
- 実在する組織名、接続先、IP、パス、ユーザー識別子、秘密値、鍵フィンガープリント、環境変数名の実一覧は公開資料に含めない。
- 実環境の構成・件数が推測できる情報も、公開レポートではカテゴリへ一般化する。
- すべての調査結果を **確認事実 / 推定 / 提案 / 未確認** に分け、確認元と確認日を付ける。
- **公開前レビューを独立した必須ゲート**とする。文書・PR本文・コメント・コミットメッセージ・差分・画像・CIログを含め、運用方式・権限範囲・設置場所・実在のホスト/サービスの識別可能性を点検する。判断できない情報は公開せず、人間へ確認する。
- 公開文書では「実際に使用中」「現在保存している」等の**実運用を示唆する断定をしない**。具体的な運用方式が必要なら仮想ケースとして明示する。一般化された構成の組み合わせでも実環境の識別につながる可能性がある。
- 公開Gitリポジトリに一度コミットした情報は、後でファイル・PR本文を直しても、**コミット履歴・既存の通知・外部キャッシュから確実に消せるとは限らない**。公開前の差分検査を最優先し、事後に露出が判明した場合は履歴だけに頼らず失効・ローテーション・関係者への通知要否を評価する。

## 4. ローカルPCの棚卸し（秘密の実値を扱わない）

対象は一般化された実行経路だけ。次の質問に回答できる範囲で調査する。

1. AIコーディングツールはWindowsネイティブ、WSL2、コンテナ、VM、リモート実行のどれか。
2. AIプロセスと秘密を置く領域は同じOSセキュリティ主体（ユーザー/権限）か。
3. AIからシェル操作、ファイルアクセス、ネットワーク接続、任意コマンドがどの程度許可されるか。
4. SSHクライアントはOpenSSH等のどれか。ssh-agentを使えるか（鍵一覧・接続先情報は取得しない）。
5. SSH接続後の作業は、通常権限とsudoがどのように分かれているか。パスワード入力にAIが関与しているかは**方式のみ**分類する。
6. 定期・無人・並列実行中に、毎回の確認が発生すると停止するワークフローがあるか。
7. 取得済みの秘密や認証可能なAgentソケットを、別タスクのAIが使い回せる構成か。
8. シェル履歴、ツール出力、ログ収集、クラウドモデル送信、デバッグ記録に秘密が載る**構造的可能性**があるか（実履歴の内容は読まない）。
9. 現行の秘密の保管形式は、ファイル / OS資格情報管理 / Agent / 外部Vaultなどの**分類だけ**で記録できるか。
10. 最低限停止できない機能（例: SSHでの読み取り調査、Draft PR、限定サービス再起動、無人テスト）を利用者の要件として整理できるか。

記録例（架空・値なし）:

| 対象 | 方式（一般化） | AIからの利用可能性 | 危険度 | 未確認事項 |
|---|---|---|---|---|
| 認証A | repo外設定ファイル | 同一ユーザーなら読める可能性 | 高 | 実際のACL |
| 認証B | SSH Agent | 署名要求が可能な可能性 | 中〜高 | 制約・承認 |
| 権限C | リモートsudo | 管理操作が可能 | 高 | 許可コマンド範囲 |

環境情報を得られない場合は、推測して埋めない。静的設計を進め、「要手動確認」に残す。

## 6. 脅威モデルと信頼境界（必須）

次の主体を分け、データフロー図を作る。

- A: AIエージェント（モデル・ツール呼び出し・子プロセス）
- B: Agent実行用OSユーザー/コンテナ/VM
- C: kinko Vault（暗号化された秘密と復号の仕組み）
- D: Broker（ポリシー検証・資格情報利用・監査）
- E: ポリシー管理者（AIが書き換えられない主体）
- F: SSH接続先とremote sudoers
- G: 外部API/GitHub等
- H: ローカル/クラウドのログ・CI・AIモデルへの出力

**問い:** AIが任意のPowerShellを実行でき、B・C・Dが同じWindowsユーザーなら、C/Dの秘密・ソケット・設定を読めない/操作できないという保証は成立するか。原則、**同じユーザー領域のCLIラッパーだけでは強い隔離と見なさない**。保護を実現するOS境界または別ホストが必要か明示する。

脅威・攻撃面のチェック:

- ファイル/環境変数/コマンドライン/シェル履歴/PTY/標準出力/例外メッセージからの流出
- AIが `kinko get`、直接SSH、裸のsudo、Agent socketへのアクセスでBrokerを迂回
- ポリシー変更、allowed wrapperの書き換え、symlink・パスの差し替え
- 許可済みコマンドの引数を使った権限拡大、任意シェル・エディタ・インタプリタの悪用
- リモートのコマンド出力、依存ファイル、Webコンテンツを介したプロンプトインジェクション
- 任意URLへのAPIキー誤送信（Host/メソッド/パス/リダイレクトの検査）
- 時間制限後のgrant再利用、他エージェントによる同じ権限・ソケットの使い回し
- マシン乗っ取り時と通常のプロンプトインジェクション時を混同しない
- Windowsプロセス環境、Named Pipe ACL、DPAPIユーザー範囲、WSL2/VMの境界、Broker起動権限

各攻撃面を **資産 / 攻撃者能力 / 成功条件 / 防御策 / 残留リスク / 検証方法（合成環境）** で説明する。実環境への侵入・迂回試験は禁止。

### 6.1 エージェントの本人確認・セッション拘束・承認の独立性（必須追加）

**APIキーやSSH秘密鍵をBrokerへ隔離しても、誰でもBrokerを操作できれば保護にならない。** 少なくとも次の設計論点を比較し、認証・認可を分けて記載する。

- **主体の認証:** 単なるプロセス名・PID・任意のHTTPヘッダー・環境変数・作業ディレクトリだけでAIの本人確認を済ませない。別OSユーザー/VMの実行主体、IPCのACL、短命のクライアント証明書・認証トークン等を候補とし、盗難・偽装・再利用の残留リスクを説明する。
- **スコープの束縛:** grantを *主体・実行セッション・対象・操作・リポジトリ/作業単位（必要な場合）・期限・利用回数* に紐付ける。セッションIDの自己申告だけを信頼せず、偽装耐性を評価する。
- **使い回し対策:** 複数AI、同一ユーザーの別プロセス、再起動後のセッション、子プロセスからの利用、盗まれたIPC資格情報を扱う。nonce/replay防止、失効・期限切れ、権限の同時使用・競合を設計する。
- **管理者の独立:** エージェントは自身のpolicy・認可済み操作・監査記録を変更できない。承認UIや短期grantの発行は別認証経路とし、「AIが承認リクエストと承認応答を両方生成する」方式を不可とする。
- **権限の実効性:** 呼び出し元を識別できても、同一OSユーザーがBroker設定・鍵・ソケットを直接扱えるなら実効的な隔離はない。前提と限界を明示する。
- **監査設計:** 認証された主体・grant ID・対象・操作・許可/拒否・期限・相関IDのみを記録し、秘密値、認証トークン、機微なコマンド出力は原則記録しない。ログの改ざん・削除可能性も比較する。

### 6.2 ネットワーク出口制御・Broker経由の情報持ち出し対策（必須追加）

認証情報の*実値*を隠しても、承認されたAPI・SSH・ツール出力を通してデータを持ち出せる場合がある。以下の防御層を区別する。

- HTTP: 許可された**宛先・メソッド・パス・ホスト・ポート**だけでなく、DNS再解決、リダイレクト、TLS検証、プロキシ迂回、内部アドレス向けのSSRF、API権限範囲を検討する。
- SSH: 指定されたホスト/コマンドに限っても、リモート側から任意の外部URLへ送信できる、ポートフォワードで迂回する、許可コマンドが任意のファイルを読める等の危険がある。**Broker側ポリシーとサーバー側のネットワーク・実行権限制御を別々に評価**する。
- 作業端末: Brokerで管理する経路の外に、AIのPowerShell/ネットワークツール/別プロセスが存在する場合、直接外部へ送れる可能性がある。OS・VM・コンテナの出口制御、接続先allowlist、不要な通信の拒否を候補とする。
- 出力: ログ/HTTPレスポンス/SSH標準出力にシークレットや個人情報が混ざる場合のマスキング・遮断・最大長・監査を検討する。ただし**一般的な正規表現によるマスキングだけでは完全なDLPにならない**。
- 運用: 自律性が必要な開発・検証操作と、外部送信や高機密データの参照を分ける。DLPと可観測性には限界があることを残留リスクへ記載する。

### 6.3 既存認証情報の漏洩疑い・事故対応計画（必須追加）

この調査の段階では実際の資格情報を読まず、失効・変更もしない。**後続作業として、以下の手順書案だけを作る。**

1. 発見・初動: 漏洩を疑う事象、連絡先/責任者、事象の発生時間・範囲・影響を評価する基準を定義する。公開ログやAI会話・履歴から**秘密値を再取得して確認することはしない**。
2. 被害拡大の抑止: 当該キー/トークン/SSHアクセス/管理権限を停止・制限する手順案を種類別に作る。緊急停止の権限を持つ人間と、通常のロールバックを明確に分離する。
3. ローテーション: APIキー再発行、SSH鍵・authorized_keysの更新、sudoパスワード変更、共有資格情報の廃止等を優先度順に整理する。**新しい秘密が旧ログやAIに再露出しない移行経路**を設計する。
4. 影響調査: 認証ログ・プロバイダーの監査記録・利用回数・費用・時間帯などを、人間の承認と守秘方針のもとで確認する計画を作る。本文には実ログを載せない。
5. 復旧・通知: 失効検証、関係者通知要否、権限の再付与、サービス継続の優先順位、記録保全と事後レビューの責任者を決める。
6. **既存の平文保存やAIへの露出は「漏洩済み」と断定しない**。観測できる証拠と可能性を分け、緊急度とサービス停止の影響も考慮する。

トークンの失効とパスワード変更だけで、既に取得されたデータが戻るわけではない点も明記する。

## 7. 自律性を維持する権限設計

### 7.1 権限階層

| レベル | 例（すべて合成例） | 期待動作 |
|---|---|---|
| L0 読み取り | `uptime`、ステータス、限定ログ | 定義済み対象なら自動 |
| L1 限定変更 | 特定のテスト環境でのアプリ再起動、Draft PR作成 | 対象・条件・時間が一致すれば自動 |
| L2 重要変更 | 新規の設定変更、パッケージ導入、未知サービスの操作 | 別経路で承認、短期grant発行後に再開 |
| L3 高危険 | rootで任意コマンド、資格情報出力、権限変更、破壊的変更 | 原則拒否。例外は実行単位の人間承認 |

**禁止:** `NOPASSWD: ALL`、広範なrootシェル許可、ワイルドカードで任意引数を許すsudoers、AIにsudoパスワードを stdin / 環境変数 / 引数で渡す設計。

sudoを自動化する場合は、root所有でAIから書き換えられないwrapper、固定の許可引数、対象制限、作業ディレクトリ・PATH・入力ファイル・symlinkへの注意が必要。「NOPASSWDだから危険」「NOPASSWDだから安全」ではなく、**何を実行できるか**を評価する。

SSH Agentを使う場合も「秘密鍵を渡さない」ことは「署名を無制限に使わせてよい」ことと違う。鍵の用途/接続先/寿命/確認機構、host key検証、Agent forwardingを確認する。

### 7.2 コマンド / API の認可モデル

提案するポリシーの最小フィールド（仮案）:

- `principal`: AIプロセスを識別するOS境界・認証された主体
- `capability`: 例 `ssh.command`、`http.request`、`service.restart`
- `target`: 事前に許可されたホスト/サービス（実名を公開しない）
- `operation`: コマンドテンプレ・HTTPメソッド・APIパス・許可引数
- `expires_at` / `max_uses`: 期限・回数上限
- `session_binding` / `request_nonce`: 認証済み主体に拘束された短命セッションとリプレイ防止（仮案）
- `approval`: 自動 / 追加承認 / 拒否
- `reason` / `audit_id`: 理由と監査の相関ID

**原則deny-by-default / fail-closed**。AIが勝手にpolicyやgrantを追加・承認できてはいけない。
承認のUXと、承認待ちでの自動作業の一時停止・再開方法も要件として扱う。

### 7.3 比較する実装配置

A. 同一ユーザーのCLIラッパーのみ: 追加が容易だが強い隔離不可。**暫定案**。
B. Windowsの別OSユーザー/保護されたサービス + 認可IPC: 端末内完結、ACL・トークン設計が重要。
C. 隔離VM/専用環境のBroker: AIとのファイル/プロセス境界は改善するが運用・同期・通信が増える。WSL2を無条件に堅牢な境界と見なさない。
D. 別ホストのBroker/SSH Gateway: 認証情報をAI端末から排除しやすいが可用性・通信・運用・復旧の設計が必要。

各案の比較指標: **自走停止率 / 人間承認頻度 / 実値露出経路 / 不正操作面 / Windows実装工数 / バックアップ/復旧 / オフライン性 / 保守負担**。

自走性の実測指標は、少なくとも次を設計する:

- 事前に許可した定型タスクが人間の追加操作なしに完了する割合
- 新規権限を求めて停止した回数/タスク・停止理由
- 誤許可/誤拒否、再実行負荷、復旧時間

## 9. 段階的な導入案を作る（このタスクでは導入しない）

1. **Phase 0: 見える化** — 現状の権限・データフロー・リスクを一般化。無変更。
2. **Phase 1: 動かし方の分離** — AIが直接平文ファイルを読む経路を特定し、別ユーザー/環境の実現性を評価。
3. **Phase 2: SSH認証の分離** — 専用鍵、OpenSSH Agent、SSH Gatewayのうち実装負担の少ない方式を選ぶ。接続先/host key/署名権限を制限。
4. **Phase 3: sudoの限定委譲** — 個別wrapperと許可対象を設計。必要なら期限付きgrant。rootの無制限委譲を標準にしない。
5. **Phase 4: API Broker** — `kinko run` とBroker方式を比較し、エージェントへ認証情報が届かないHTTP/API実行を検証。
6. **Phase 5: 監査・多重化・復旧** — 並列Agent、無人実行、期限切れ、監査、停止・復旧を設計。
7. **Phase 6: Shadow評価と限定並行稼働** — 既存方式の処理結果と新方式の**許可判定**を比較する。Shadow modeでは実SSH/sudo/API操作を重複実行せず、機微な値を複製しない。合成環境で性能・停止率・誤許可を評価してから、ごく限定した低リスクの実運用対象への移行可否を別途承認する。
8. **Phase 7: Canary移行と切り戻し確認** — 対象・機能単位で一方だけを操作実行系とし、同一の高権限操作を旧新両経路から同時に実行可能にしない。Broker障害時の自動的な旧平文経路へのフォールバックは禁止する。代替手段が要る場合、人間の明示承認・期限・監査を条件とする。
9. **Phase 8: 旧資格情報の失効・撤去** — 新方式のテスト、切り戻し手順、監査、業務継続を確認したあとに、旧資格情報を**失効・ローテーション**して段階的に撤去する。**先に削除しない**。既存平文ファイル、バックアップ、シェル履歴、CI/AIログの扱いは別途人間の承認と影響評価が必要。

各Phaseについて、前提条件、成功指標、残留リスク、ロールバック、利用者の承認ゲートを明記する。

### 9.1 並行稼働・切替判定の定義

- **ShadowとDual-writeを混同しない:** 判定の比較は可能でも、デプロイ・sudo・API書き込み操作の二重実行は副作用があるため行わない。
- **機能と認証情報を分離:** 旧経路と新経路の同時利用を最小化し、平文ファイルを新設・複製しない。切替対象に紐付く一時権限は失効可能にする。
- **切替条件:** 合成環境でT01〜T19を確認し、実環境移行前には利用者の別承認を要する。自走率、停止回数、誤許可/誤拒否、操作時間・復旧時間に許容範囲を定義する。
- **切り戻し:** 監査つきの安全な戻し方を定義するが、AIが独断で長期秘密や無制限sudoへ戻す経路は設けない。緊急時の運用責任者と停止判断を明確にする。
- **完了条件:** 認証情報の更新・旧権限の失効・不要ファイルの安全な撤去・監査確認までを追跡し、単なる「新ツールで接続できた」を完了としない。

## 10. 比較・結論の作り方

最低でも次の3案を比較し、結論を決め打ちしない。

- **案1: kinkoを最小拡張** — 既存の保管庫 + 外部OpenSSH Agent/限定sudoers。小さく始める。
- **案2: kinko + Broker** — 既存CLIと保管庫は残し、別権限のbroker / policy / audit / grantを追加。
- **案3: 既存OSSを採用** — SSHやHTTPの仲介を既存ツールに委ね、kinkoは保管・CLIに専念。
- 必要なら案4: **統合またはfork**。著作権・ライセンス・保守とセキュリティ更新を評価した場合のみ。

比較には、守りたい秘密・許可したい作業・許容される人間確認・単一障害点・本番投入条件に加え、**主体認証とセッション拘束 / 通信の出口制御 / 漏洩時の復旧 / 旧新方式の切替リスク**を必ず含める。
安全性を高く見せるためにAIの自律性を大幅に落とす案も、自律性を優先して実質無制限rootを許す案も、**トレードオフを数値/条件付きで説明**する。
