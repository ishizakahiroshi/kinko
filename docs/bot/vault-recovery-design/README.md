# #P-20261012-004 kinko：金庫を失っても戻せる方式の検討

この文書を読んだdots担当は、既存調査と固定sourceを読み、復旧方式を検討し、推奨案と根拠を日本語HTMLにまとめ、別担当の独立レビューと必要修正を経て固定commitで提出する。検討のみ。製品を実装しない。

## 目的と未決定の出発点
利用者は金庫を設定した後の誤削除やPC・disk全損を心配している。前案件で1Passwordの救済条件とkinkoの不足を調査済み。今回は「kinkoでどう備えると、普段の操作を増やさず事故後に戻せるか」を検討する。
手元AIが挙げた4つは仮説であり、本人の採用決定ではない。
- 更新・削除前の状態を暗号化したまま自動保持。
- PCとは別の場所に、削除操作が連動しないcopyを保持。
- copyを開く解除情報を金庫以外にも確保。
- copyから実際に取り出せる確認を経て準備完了と表示。
4つを鵜呑みにせず、不足・過剰・矛盾と失敗経路を検討し、よりよい案があれば理由付きで推奨する。

## 検討すべきこと
1. **事故と守れる範囲**: 項目誤削除/誤更新、金庫file全削除/破損、PC全損、マスターパスワード紛失、端末解除機能の消失を分ける。悪意あるOS管理者、侵害済OS、全copyと全解除手段の同時喪失まで救えると主張しない。
2. **初期設定→通常利用→復元の使い方**: 何を利用者が一度だけ指定・保管するか、普段は何が自動か、別端末で何を選んで戻すかを短い例と図で示す。通常の起動やgetに毎回backup設定を要求しない。CLI方式は維持。
3. **世代保存**: 新規作成時と初回secret追加後、更新前後、削除前に何を保管するか。同じdirectoryに全copyを置く問題。保存中断・競合・空き容量不足・破損・誤password・古いversion・二重実行に対し、原本と最後の正常世代を壊さない境界。backup日時だけでなく、対象金庫/世代の同一性、復号できること、必要項目の確認を含む。
4. **PC外のcopy**: 元の削除や同期削除に巻き込まれない保管をどう実現するか。普通の同期folderと独立backupを同一視しない。利用者の既存媒体/別PC/既存backupを使う案と、製品から外部保管へ接続する案などを、現実に成立する案だけ比較する。未設定/切断/未転送/障害/認証紛失時に、どこまで保護できているかを正直に示す。既存の実保存先やaccountは未指定。
5. **鍵を忘れた事故**: 使用可能な端末解除、別passwordのexport、全解除手段の喪失を区別する。緊急用の解除情報/紙への保管を提案する場合は、対象世代との対応、更新、紛失、漏洩、再発行、無効化の意味を示す。新しい復旧鍵を提案するならageの現行recipient制約・既存format1読み込みとの互換を公式資料/実装で確認し、独自暗号を設計しない。
6. **履歴保持と消去**: 保存数/期間の根拠、容量との兼合い、昔の秘密や失効済秘密がbackupへ残ること、利用者が本当に消したい場合との整合。保管先がimmutableでも全消去や失効を無条件に保証しない。
7. **成功/失敗の扱い**: local世代の保存失敗とPC外転送失敗を分け、既存secretを読む操作と書き換える操作を分ける。offline時の利用と安全性のtradeoff、再試行/通知/最新成功時刻の表示、復元先の非上書き、backupへの復元操作の逆流を検討。
8. **最小の実用範囲**: 「復旧の備えが整うまで使えない」か「限定保護で試せる」か等の利用者体験。最初の提供範囲、後段の拡張、開始前に必要な実機/複製データの検証を示す。将来の独立した復旧指針/テストmatrixは設計資料まで。製品testを追加/実行しない。
9. **提案の採否**: 推奨案を1つと、その利用者メリット/不利益/成立条件を明示。作る手間や検査のしやすさを推奨理由にしない。手間は改修目安の欄だけに概算/不確かさ付きで置く。内部で決められる実装判断を本人への質問にしない。保存先など実際に本人の情報が必要な点だけ末尾へ残す。
10. **現行scopeとの関係**: CLAUDE.md/referenceは現状であり自動復旧/cloud同期は現在scope外。今回変更しない。提案としてscope拡張が必要な箇所と、既存ルール改訂が必要な箇所を説明する。制約だけで利用者に有利な案を除外しない。
